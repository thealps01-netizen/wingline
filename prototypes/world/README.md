# World prototype: one continuous zoom from planet to port

A standalone prototype of the Board's zoom. The plugin does not load it. It shows the
Kanban as one world, at three levels of the same scene:

- **Planet**: one area per board.
- **Region**: one board. Each pipeline is a settlement whose type follows its spend: under
  $4 a farm, $4–10 a village, over $10 a port.
- **Port**: one pipeline. Each berth is a task; the cranes and trucks are the agents.

There is one camera and one render pass. No scene is swapped or crossfaded. Fine detail
(trees, berths, trucks) fades in at its own place once it is big enough on screen. The
user rejected crossfades between separate scenes: they read as a jump and left bare
stretches.

## Data

- **Boards, pipelines, task counts and spend** are a snapshot of a real Hermes Kanban,
  embedded in `planet.base.js`.
- **Staged data:**
  - The task states inside the port (which crane is working or done).
  - The click on `note-actions r1` at 13.1 s.
- **Real data:** `planet.html?view=world&data=<file>` draws a live Kanban instead of the
  snapshot. The file is the plugin's own converter output (`worldOf` in `desktop/plugin.js`),
  made with `node world-data.mjs <overview.json> data-<name>.json [board slug]` (needs
  `cd ../../tests && npm ci` once; `data-*.json` is not tracked). The open board is the region;
  the camera flies on down to the pipeline `worldOf` ranks first and builds it in its own kind:
  a port (a berth per task), a village (a workshop per task on the main street) or a farm (a field
  per task). Without `data=` the page is the snapshot, pixel
  for pixel (10 canvas hashes, `canvas-eq.cjs`).
- **Stable rebuilds:** settlements are laid out in pipeline-key order, each draws its random numbers
  from its own key, and the file may carry `keepSites` (the spots of the last build, which the page
  leaves in `window.__siteSpots`) and `focus` (the pipeline key to fly down to). A rebuild after one
  task changed state then differs only at that settlement, the HUD numbers and the labels that
  make room (Sap Systems, one task done → running: 1,751 of 1,062,000 region pixels, 0 at the site).
  Labels carry `data-id` (board slug, pipeline key or task id) for clicks.
- **Not done yet:** a board with no pipelines stops with a note; real clicks, live updates and the
  agent stream. That is the plugin integration step.

## Files

`build.sh` turns the sources into `planet.js` in this order: `planet.base.js` →
`world_patch.py` → `data_patch.py` → `speedup.py` → `slice.mjs` → `fallback.py`.

| File | Role |
|---|---|
| `planet.base.js` | Base scene code: drawing helpers, the planet, region and site builders, and the older three-scene `view=descent`. |
| `world_patch.py` | Turns `planet.base.js` into the world view. Every replacement must match exactly once, so a drifted base fails loudly. It also inlines `world.part.js`. |
| `data_patch.py` | Real Kanban data with `data=<file>`: boards and labels on the planet, the open board's pipelines as settlements, the port pipeline's builder, reviews (up to 6 cranes) and gate, and the HUD from `worldOf`'s chrome. Trucks stand still while no task of the port is working. |
| `world-data.mjs` | Makes a `data=` file from a Kanban overview with the plugin's own `worldOf`. |
| `world.part.js` | The world view itself: the region draped onto the planet, the port model placed inside the region, the level-of-detail line shaders, the camera timeline and the HUD. |
| `speedup.py` | Load-time speed-ups that keep the picture the same: outline edges are computed once per shape and reused, the region height field is memoised, and the river distance check skips far chunks. The full measurement gave the same numbers before and after. |
| `slice.mjs` | Makes the build pause every 12 ms, so the page keeps responding while it builds. It parses `planet.js` (acorn) and turns the build functions into generators with pause points in their loops and between their steps; the GPU compiles the shaders in the background before the first frame. A loading line ("Charting 7 boards") stands in for the HUD meanwhile. Recorders (`rec=1`) still build in one go. |
| `fallback.py` | Shows a note instead of the world when the computer draws it too slowly: no WebGL2 or a software renderer (checked before building), or under 30 fps (median of frames 10–40 after the build; throttled background frames are ignored). In the plugin the note becomes the Board view. |
| `planet.html` | Page shell. It loads three.js through an import map. JS errors and `console.error` are collected in `window.__errs`, and every harness fails on them. |
| `planet.js` | Generated by `build.sh`. Not tracked. |

## Running

Set up once with `npm ci`, which installs three.js 0.186.1 and the build's parser (acorn
8.19.0, acorn-walk 8.3.5), all pinned. Then start `python serve.py 8799` and keep it
running. The server sends `no-store`, because a caching server made Electron replay a stale
`planet.js`.

| Script | What it does |
|---|---|
| `bash build.sh` | Generates `planet.js`. Fails on a syntax error, and on a `//` comment that hides code on the same line (`comment_lint.py`). |
| `bash probe.sh [T0] [T1] [FPS]` | Builds and writes `world-sheet.png`, a contact sheet for a look by eye. |
| `bash measure.sh [FPS]` | The full picture check, about 6 minutes at 100 fps. |
| `bash load-check.sh` | The load checks, about 3 minutes: no freeze, same world when paused, both fallbacks, no fallback on this machine. Prints PASS or FAIL per check. |

To see the view, open `http://127.0.0.1:8799/planet.html?view=world`. It renders in any
WebGL2 browser. Query options: `gpu=any` skips the software-renderer check, and `minfps=N`
changes the frame-rate minimum.

The recorders need an Electron binary. By default they use the one inside the Hermes
desktop install; set `ELECTRON` to use another. `load-check.sh` opens one real window
off-screen for a few seconds, because hidden windows are throttled to about one frame per
second.

## Acceptance limits (`measure.sh`)

| Check | Limit | Last result (2026-10-20, 100 fps, AMD RX 9070 XT) |
|---|---|---|
| Camera speed, every phase | ≤ 2 px per 10 ms, no kinks | 1.79 max (flight to the port) |
| Flicker per phase (p999 of the tile second difference) | < 7 | 4.78 max |
| Coverage (share of tiles with drawn lines) | never under 35 % | 41 % min (orbit, open space), 73 % median |
| Wide simultaneous change (scene jump) | — | 2.8 % max, at 15.8 s; frames look identical by eye |
| JS errors, label overlaps | none | none |

Numbers only rule out regressions. Contact sheets and single frames were also checked by
eye, because none of the metrics catches a bare stretch or a giant foreground object on
its own.

## Load time and frame rate (2026-10-20, AMD RX 9070 XT)

| | Result |
|---|---|
| Building the world, offscreen | 5.3 s at first; 2.7 s with `speedup.py`, as one 2.8 s task (the page froze); 3.5–3.8 s with `slice.mjs`, no task over 50 ms (longest slice 38–45 ms: the first frame) |
| Inside Hermes Desktop, as a trial plugin with three.js bundled in (827 KB, before `slice.mjs`) | 3.7 s build; Hermes' own import check accepts the bundle |
| Frame rate in the real window | 180 fps for 30 s (the display's limit), no frame over 20 ms; 179 fps at pixel ratio 2 |
| Software rendering (no GPU, SwiftShader) | 2 fps, so `fallback.py` shows the note before anything is built |

## Not verified

- Integrated laptop GPUs and real high-DPI screens (pixel ratio 2 was only simulated).
- The 50 ms limit on a slower CPU: the first frame alone took 38–45 ms here.
- The sliced build inside Hermes Desktop (measured in a plain Electron window).
- Boards other than the snapshot, an empty board, and narrow windows.
